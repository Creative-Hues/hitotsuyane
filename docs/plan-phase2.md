# フェーズ2の計画:データに関わる機能追加

## 結論

- データベースの版を 6 → 7 に上げ、次の3つのデータの変更を1回の版上げにまとめる
  - ToDo の周期に「期限なし」を足す
  - バケットに出す人格の一覧(新しいテーブル)を足す
  - 交代の記録に「交代前の人格」と「推測か・確認したか」を足す
- 版を上げる前に、今のデータを端末の中に自動で写しておく仕組み(移行前の自動バックアップ)を最初に作る
- 新しく足すデータは、すべてバックアップの書き出し・読み込みに入れる。古いバックアップも読み込める
- フェーズ2の前に、更新のお知らせが出ないことがある不具合を直し、先に本番に入れる(「準備」の章)。フェーズ2の移行を、お知らせから確実に始められるようにするため
- 7つの段階に分ける。テスト版に反映する前と、main にマージする前に止まる(データの形が変わるので、マージの前に必ず声をかける)
- 確認したいことには答えをもらった(この計画の最後の「決まったこと」)

## 準備:更新のお知らせが出ないことがある不具合を直す(データは変えない)

### 起きたこと

- フェーズ1を本番に入れたあと、本番のアプリを開き直しても、お知らせが出ず古い画面のままだった
- 本番のサイトには新しい版が正しく置かれていた(`sw.js`・`version.json`・オフライン用の19個のファイルがすべて読める)。原因はサイトではなく、アプリ側で新しい版に気づくしくみにある

### 今のしくみ(お知らせが出る条件)

- 新しい版に気づくのは、次の2つのとき
  1. アプリを開いたとき(読み込み直したとき):オフライン用の仕組み(サービスワーカー)を登録するときに、ブラウザがサイトの `sw.js` を確かめる
  2. 画面に戻ったとき:アプリが `sw.js` をもう一度確かめる
- `sw.js` が変わっていると、新しい版のファイルを裏で全部取ってきて、取り終わると「待っている版」になる。そのとき帯を出す

### 原因(見込み)

- 帯を出す合図を、使っている部品(workbox-window)が見落とすことがある
  - アプリを開いた直後、部品の準備ができる前にブラウザが新しい版を見つけて取り始めると、部品は「取り始めた」合図を受け取れない。その回は帯が出ない
  - そのあと画面に戻っても、`sw.js` は取り終えた版と同じなので「新しい版が見つかった」合図が出ない。アプリ側は「待っている版」があるかを自分では確かめていないので、帯が出ないままになる
  - iPhone のホーム画面のアプリは、閉じたつもりでも裏で止まっているだけのことが多い。アイコンを押しても読み込み直さず「画面に戻った」扱いになるので、この状態が続きやすい
- サイトのファイルは10分間、端末に保存される(GitHub Pages の決まり)。公開してすぐ(10分以内)だと、iPhone が古い `sw.js` を見て「新しい版はない」と判断することもある
- iPhone の中を Windows から直接のぞく方法がないため、実機での確定はできていない。下の直し方は、どちらの原因でも帯が出るようにするもの

### PC の Chrome で確かめたこと(2026-10-14)

- 手元に、本番と同じパス(`/hitotsuyane/`)・同じ保存の決まり(10分)で配る確認用のサーバーを立て、画面なしの Chrome を外から操作して確かめた
- 試した場面:①画面に戻ったとき ②新しい版を取っている途中に開き直したとき(新しい版のファイルをわざと遅く返す) ③登録から1分以上たって画面に戻ったとき
- 今の本番の版(1bf1cfa)でも、Chrome ではどの場面でも帯が出た。本番で起きた見落としは、Chrome では再現できなかった(iPhone の Safari は、新しい版の取り方が Chrome と違うため、と見ている)
- 直した版で、部品(workbox-window)の合図をわざと止めた状態を作って試した。アプリ自身の確認だけで、①〜③のすべてで帯が出て、「更新する」で新しい版に切り替わり、読み込み直した
- iPhone での確認は、テスト版で行う

### 直し方

- アプリを開いたとき・画面に戻ったときに、`sw.js` を確かめたあと、「待っている版」と「取っている途中の版」があるかをアプリ自身でも確かめる
  - 待っている版があれば、帯を出す
  - 取っている途中なら、取り終わるのを見届けてから帯を出す
- 画面を開いたままのときも、30分ごとに確かめる
- 「更新する」を押したら、新しい版に切り替わったところで、必ず読み込み直す(今は、部品が合図を受け取れたときだけ読み込み直している)
- 確かめるしくみは純粋関数とテストで確かめられる形にし、PC の Chrome で「古い版 → 新しい版」の更新を再現して確かめる
- テスト版で確かめる:直した版をテスト版に反映 → もう1回、中身を少しだけ変えた版をテスト版に反映 → iPhone のテスト版で帯が出て、更新できることを確かめる
  - 2026年10月14日:直した版(e1d9860)をテスト版に反映し、iPhone のテスト版を直した版にした。続けて、このメモを足しただけの版を2回目として反映した(アプリの版の表示が変わるので、新しい版として届く)
- 確かめたら main にマージする(データは変えないので、バックアップのお願いはいらない)。フェーズ2より前に本番に入れておくと、フェーズ2の更新でお知らせが確実に出る

### 今の本番(フェーズ1)を確実に新しい版にする方法(利用者の作業)

この不具合は、今の本番の版の中にあるので、直した版が届くまでは次の手順で読み込み直す。

1. iPhone で、画面の下から上にゆっくりスワイプして、開いているアプリの一覧を出す
2. ひとつやねを上にはじいて、完全に閉じる
3. ホーム画面のアイコンから開き直す。Wi-Fi などつながる場所で、1分ほど開いたままにする(裏で新しい版を取ってくるため)
4. もう一度 1〜3 をする。帯が出たら「バックアップを書き出す」→「更新する」
5. 人格タブの「このアプリについて」の版が `2026.10.14(1bf1cfa)` になっていれば、新しい版
- **ホーム画面のアイコンは削除しない**(iPhone では、アイコンを削除すると、そのアプリの中のデータも消えるため)

## 前提

- この計画は、`dev`(1bf1cfa フェーズ1 段階D。main と同じ)のコードを元にしている
- 画面の言葉の「人格」は、今と同じしくみ(`useTerm` の `t()`)で、設定した呼び方に置き換える
- 人格の名前を出すところは、フェーズ1で作った名前ラベル(`AlterNameLabel`)を使う。選ぶための部品(大きな色のボタンなど)は今までどおり名前ラベルにしない(`SPEC.md` 5章)
- 並び替えは、すべて ≡ のドラッグで行う
- 日付・論理日(朝5時の区切り)の計算は `src/lib/period.ts` を通す。新しく作る計算(交代前の推測・カレンダー・きっかけの集計)は純粋関数(同じ入力なら同じ結果)にしてテストを書く
- 保存の名前(移行前の自動バックアップの置き場所など)は `src/lib/appTarget.ts` を通す

## 0. 移行前の自動バックアップ(このフェーズの土台)

既存のデータを守るため、データベースの版を上げる前に、今のデータを丸ごと写しておく。

### しくみ

- アプリを開いたとき、端末の中のデータベースの版が、アプリの版(7)より古いかを先に確かめる
  - 古いときだけ、版を上げる前に、今の版のままデータを読み、バックアップと同じ形の JSON にする
  - それを、別の小さなデータベース(名前は `appTarget.ts` で決める。本番とテスト版で分ける)に「移行前のバックアップ」として保存する
  - 保存できたことを確かめてから、版を上げる(移行処理)
  - 写しの保存に失敗したときは、版を上げずに止め、「データの準備ができませんでした」と出す(データは古い形のまま残る)
- 新しく入れた人(データベースがまだない人)には何もしない
- 写しは、次に版を上げるまで残す(次の版上げで、新しい写しに置き換える)

### 画面

- 更新した直後(移行が終わって最初に画面が出たとき)に、画面の上に帯を出す
  - 文:「更新前のデータを保存しました。書き出しておくと安心です。」
  - ボタン:「書き出す」(その場で更新前のデータをファイルにする。iPhone では共有シートが開く)・「閉じる」
  - 書き出すか「閉じる」を押すまで、開くたびに出す。閉じたあとも、バックアップ画面から書き出せる
- バックアップ画面に「更新前のデータ(○月○日)」の欄を出し、「書き出す」ボタンでふつうのバックアップと同じようにファイルにできる
  - 書き出したファイルは、今までのバックアップと同じように読み込める(古い形のファイルとして読み込む)
- iPhone では、ボタンを押さずにファイルを「ファイル」アプリに保存することはできない(共有シートは指で押したときだけ開けるため)。そのため「自動」は端末の中に写しておくところまでで、ファイルにするのは利用者の操作になる

### なぜ必要か

- 更新のお知らせ(`SPEC.md` 18章)を見ずに更新した人や、お知らせの出ない古い版から更新した人でも、移行で何か起きたときに元に戻せるようにするため
- フェーズ3・4でも版を上げるので、このしくみはその後も使い回す

## 1. ToDo に「期限なし」を追加

### データ

- 周期(`Cycle`)に `{ type: 'none' }`(期限なし)を足す
- 完了は、今までと同じ完了記録(`CompletionRecord`)で残す(誰が・いつ。集計の「代行」にもそのまま数えられる)
- 今の完了記録は1年たつと自動で消える(`SPEC.md` 3.3)。期限なしのタスクの記録が消えると、完了済みのタスクが「未完了」に戻ってしまう
  - そのため、**期限なしのタスクが残っている間は、そのタスクの完了記録を1年の削除の対象から外す**
  - タスクを削除したあとは、今までと同じく1年で消える

### 画面(リストの ToDo)

```
期限なし
 □ 粗大ごみの申し込み     人格A
 □ 印鑑を探す
 ▸ 完了済み(3件)          ← 折りたたみ。最初は閉じている
今日
 ...
```

- ToDo 画面の一番上に「期限なし」の欄を出す(今日・今週・今月より上)
  - 未完了を上、order 順。タップで今までと同じく人格を選んで完了にする
  - 完了すると、欄の下の「完了済み」に移る。完了済みは、完了した日時の新しい順に「人格A・10/14 9:12」の形で溜まる
  - 完了済みをタップすると、今までと同じ取り消しの確認が出て、未完了に戻せる
  - 完了済みの中に「選択」ボタンを置き、複数選んで「○件を削除」できる(確認を1回出す。タスクの削除と同じルールで、完了記録は残す)
- ToDo 画面の上のボタンの並びに「+ 追加」を置く([+ 追加][並び替え][タスク設定])
  - 押すと、期限なしの ToDo の入力画面が開く(名前・気にしている人格だけ。周期は「期限なし」に決まっている)。思いついたときにすぐ足せるようにするため
  - ほかの周期のタスクは、今までどおり「タスク設定」から足す
  - 期限なしの ToDo が1件もないときは、「期限なし」の欄を出さない(今の欄と同じ)
- 前の期間の表示(`SPEC.md` 6.5)は、期限なしのタスクには出さない
- 並び替えモードでは、期限なしの未完了の中で ≡ で並び替える
- タスク設定の周期の選択肢に「期限なし」を足す

## 2. バケットを「人格を追加する方式」に変更

### データ

- 新しいテーブル「バケットに出す人格」を足す

| 項目 | 説明 |
|---|---|
| alterId | 人格のID(主キー) |
| hidden | バケットから外したか(外しても消さない) |
| addedAt | 追加した日時 |

- 並び順は人格の並び順を使う(バケットだけの並び順は持たない)
- バケットの項目(`BucketItem`)は書き換えない
- 版を上げるとき:今使っている人のバケットを、見た目が変わらないよう引き継ぐ。今バケットに出ている人格(非表示でない人格)全員を入れる
- 新しく入れた人は、空から始まる

### 画面(リストのバケット)

- 人格の切り替えボタンの並びの最後に「+」ボタンを置く
- 「+」を押すと、登録済みの人格の一覧が出て、選ぶとバケットに追加される
  - 出すのは、非表示でない人格のうち、まだバケットに出ていない人格(並び順)
  - 前に外した人格は「外した人格」として同じ一覧に出し、選ぶと再表示する(項目はそのまま戻る)
- バケットの人格が0人のときは「バケットに出す人格を「+」から追加してください」と出す
- 外すとき:人格のリストの画面に「この人格をバケットから外す」を置き、ふつうの確認を1回出す(本人確認の形にはしない。項目は消えず、再表示すると戻るため)
  - 確認文:「人格Aをバケットから外しますか?リストの項目は消えず、「+」からまた出せます。」
- 人格そのものを非表示にした人格は、今までどおりバケットに出さない
- 人格を削除するとき(`SPEC.md` 3.1)は、「バケットに出す人格」からも外す。バケットに出しているだけ(項目がない)なら、削除できない理由には数えない

## 3. 交代記録に「誰から誰に」を追加

### データ

交代の記録(`SwitchLog`)に2つ足す。

| 項目 | 説明 |
|---|---|
| fromAlterId | 交代前の人格のID。「わからない」は null |
| fromAlterSource | `'guessed'`(推測のまま記録)/ `'confirmed'`(「交代前の人格を修正」で選んだ) |

- 推測のしかた:記録の時刻(`SPEC.md` 17.3。交代した時刻、わからなければ気づいた時刻)より前で、いちばん新しい記録の「交代した人格」を、交代前の人格とする。前の記録がなければ「わからない」
  - 推測は純粋関数にしてテストを書く(フェーズ3の受診前のまとめでも使う)
- 版を上げるとき:今の記録を時刻順に並べ、上と同じやり方で交代前の人格を補い、すべて `'guessed'` にする
- 交代前の人格になっている人格も、削除できない人格に数える(`SPEC.md` 3.1)。消すと「誰から」がわからなくなるため

### 記録の流れ(`SPEC.md` 17.1)

- きっかけを選ぶ段階(最後の段階)の上に、次のように出す
  - 「[人格A]さんからの交代で合っていますか?」(人格Aは名前ラベル)
  - 前の記録がない・前の記録が「わからない」のときは「交代前:わからない」
  - 前の記録が、今回記録する人格と同じときは「前の記録も[人格A]さんです。間にほかの人がいたら修正してください。」
  - その下に「交代前の人格を修正」ボタン。押すと人格の一覧(非表示でない人格+「わからない」)が出て、選ぶと表示が変わる
  - ボタンを押さずに「記録する」「わからない」を押すと、推測のまま記録する
- 時刻を「時間を指定」にしたときは、その時刻を基準に推測する(そのため、時刻を決めたあとの最後の段階で出す)

### 編集画面(`SPEC.md` 17.4)

- 「交代前の人格」を出し、直せるようにする。直したら `'confirmed'` にする(推測と同じ人格を選び直したときも `'confirmed'`)
- 推測のままの記録には、「交代前:人格A(推測)」のように小さく「推測」と添える

### 推測の計算し直し

- 記録を足した・時刻や人格を直した・削除したときは、`'guessed'` の記録だけ、交代前の人格を計算し直す(`'confirmed'` の記録は変えない)
- 計算し直しは、保存と同じ1回の処理(トランザクション)の中で行い、途中で止まっても記録が半端にならないようにする

### 一覧

- 記録の一覧の1行を「時刻・[人格A] → [人格B]・きっかけ」の形にする(交代前 → 交代した人格)

## 4. きっかけの集計画面

- 今の集計の「きっかけごと」の欄を、「誰から誰に」がわかる形にする

```
きっかけごと
音(3回)
  [人格A] → [人格B]  2回
  [わからない] → [人格C]  1回
疲れ(1回)
  [人格B] → [人格A]  1回
```

- きっかけの並び順、「わからない」(きっかけなし)は最後。1つのきっかけの中は、回数の多い順(同じ回数なら人格の並び順)
- 回数が0の行は出さない(今と同じ)
- 受診用のPDF(`SPEC.md` 17.6)も「誰から誰に」を入れる
  - きっかけの表:上と同じ形
  - 記録の一覧:「時刻・人格A → 人格B・きっかけ」(推測のままの記録には「(推測)」を添える)

## 5. 交代記録のカレンダー表示

```
‹ 前の月   2026年10月   次の月 ›
[受診用にPDF]
┌──────────┬──────────┐
│   一覧   │カレンダー│   ← 切り替えボタン(リスト・治療と同じ形)
└──────────┴──────────┘
 日  月  火  水  木  金  土
              1   2   3
             ●●  ●   ●●●
                 ●   ●●●
                     ●●+
 ...
```

- 交代タブの、月の切り替えと「受診用にPDF」の下に、[一覧][カレンダー] の切り替えボタンを置く
  - 一覧:今までの集計と記録の一覧
  - カレンダー:その月のカレンダー
  - アプリを開いたときは一覧を出す。アプリを開いている間は、最後に選んだほうを覚えておく(保存しない)
  - 月を切り替えても、選んでいるほうのまま
- 週の始まりは日曜(日〜土)
- 各日付のマスに、小さい円を最大9個(3×3)並べる
  - 円の色は、その日(論理日)に記録のあった人格の色。その日に初めて出た順(記録の時刻の古い順)
  - 同じ人格が何回出ても円は1つ
  - 「わからない」は灰色の円
  - 10人以上のときは、8個の円のあと、9個目の位置に「+」を出す
- 日付を押すと、その日の交代記録だけの一覧が開く(「‹ 戻る」あり。行を押すと編集画面)
- カレンダーのマスの組み立ては純粋関数にしてテストを書く

## データとバックアップへの影響

- データベースの版:6 → 7(更新のお知らせは「データの形が変わる」強めのものになる。`DB_VERSION` を上げると自動で `version.json` に入る)
- バックアップの版番号(`BACKUP_FORMAT_VERSION`)は上げない(`SPEC.md` 12章)。新しい項目がない古いファイルは、次のように読み込む
  - 周期:今までの4つはそのまま読める
  - バケットに出す人格がない:版上げのときと同じ決め方で、バケットに出す人格を作る
  - 交代前の人格がない記録:版上げのときと同じやり方で推測し、`'guessed'` にする
- 新しい形のバックアップ(期限なし・交代前の人格などが入ったもの)は、今の本番の版では読み込めない。テスト版で書き出したファイルを、マージ前の本番に読み込まない(`SPEC.md` 21.2 のとおり)
- 形の正しくないファイル(交代前の人格が、ない人格を指している、など)は読み込まない

## テスト

- 移行
  - 版6のデータ(人格・タスク・完了記録・服薬・受診メモ・バケット・プロフィール・交代の記録)が、版7に上げても1件も消えず、中身が変わらない(足した項目以外)
  - 版上げの前に、移行前のバックアップが保存される。保存した写しを読み込むと版6のデータに戻る
  - 新しく入れたときは、写しを作らない
  - バケットに出す人格が、決めたルールどおりに入る/新しく入れたときは空
  - 交代前の人格が時刻順に補われ、すべて「推測」になる(最初の記録は「わからない」、時刻を指定した記録・時刻がわからない記録の並び)
- 期限なし
  - 一番上の欄に出る/完了すると完了済みに移る/取り消しで戻る
  - 1年より古い完了記録でも、期限なしのタスクが残っていれば消えない。タスクを削除したあとは消える
  - 完了済みの複数削除で、選んだタスクだけ消え、完了記録は残る
- バケット:追加・外す・再表示で項目が変わらない/人格の削除で外れる/バケットに出しているだけの人格は削除できる
- 交代前:推測の関数(前の記録あり・なし・前が「わからない」・時刻を指定)/修正すると「確認」になる/交代前になっている人格は削除できない
- きっかけの集計:きっかけごと・誰から誰にの回数と並び
- カレンダー:初めて出た順・同じ人格は1つ・「わからない」は灰色・10人以上で「+」・朝5時の区切り
- バックアップ:書き出し → 読み込みで新しいデータも元どおり/新しい項目のない古いファイルを読み込める/ない人格を指す交代前の人格があるファイルは読み込まない
- 画面の確認(PC の Chrome のデバイスモード):呼び方を「メンバー」にしたとき・長い呼び方・ダークモード
