# 公開のしかたの準備案(テスト版の用意)

フェーズ1に入る前に行う準備です。アプリの見た目や機能は変えません。

## 結論

- 作業はすべて `dev` ブランチで行い、`main` には直接 push しない
- テスト版は `https://creative-hues.github.io/hitotsuyane-test/` で公開する
- テスト版は、ビルドのときの切り替えで、データベースの名前・ホーム画面の名前・公開先を本番と分け、画面の上に「テスト版」の帯を出す
- テスト版のビルドの中に、本番のデータベースの名前(`did-todo`)が入っていないことを、自動で確かめる
- テスト版の反映は、この PC から行う(ビルドした中身だけを `hitotsuyane-test` に送る)

## 今の仕組み(読んでわかったこと)

- 本番:`main` に push すると、GitHub Actions がテスト → ビルド → GitHub Pages に公開する(`.github/workflows/deploy.yml`)
- `main` 以外のブランチに push すると、テストとビルドの確認だけが行われ、公開はされない(`check.yml`)。そのため、`dev` に push しても本番は変わらない
- データの保存先
  - すべて IndexedDB の `did-todo` という名前のデータベースに入っている(リポジトリ名を変えたときも、この名前は変えていない)
  - 端末の設定(バックアップの最終書き出し日時・集計の表示・呼び方)も、同じデータベースの `meta` という表に入っている
  - localStorage・sessionStorage は使っていない
- オフライン用の仕組み(サービスワーカー)と、その保存場所は公開先のパスごとに分かれるので、テスト版と本番はぶつからない
- 更新のお知らせ用の `version.json` も、それぞれの公開先に置かれるので混ざらない

## 本番のデータを守るための仕組み

同じドメイン(`creative-hues.github.io`)では、テスト版と本番が同じ保存場所を使います。名前が同じだと、テスト版が本番のデータを直接読み書きしてしまうため、次のようにします。

1. ビルドに「テスト版」の切り替えを足す(`npm run build:test`)
   - 公開先のパス:`/hitotsuyane-test/`
   - データベースの名前:`hitotsuyane-test`(本番の `did-todo` とは別)
   - 今後 localStorage などを使うときに備えて、キー名の頭に付ける文字も本番と分ける(本番:`hitotsuyane:`、テスト版:`hitotsuyane-test:`)。保存の名前はすべて1つのファイル(`src/lib/appTarget.ts`)で決める
   - ホーム画面の名前:「テストやね」。途中で切れず、本番と見分けられるようにする
2. テスト版の画面の一番上に、「テスト版」の帯をいつも出す
   - 更新のお知らせの帯が出るときは、その上に重ねて出す
   - 本番のビルドには、帯の部品も文字も入らない
3. 自動の確認を足す(dev に push したときに GitHub Actions で行う)
   - テスト版のビルドの中に `did-todo` という文字が1つもないこと(本番のデータベースを開くコードが入っていないこと)
   - 本番のビルドのデータベースの名前が `did-todo` のままであること(テストでも確かめる)
4. バックアップのファイル名
   - 本番は `hitotsuyane-backup-2026-10-14.json`、テスト版は `hitotsuyane-backup-test-2026-10-14.json` にする(ファイル名だけ変える。中身の形とアプリの識別名 `minna-todo` は変えないので、今までのバックアップもそのまま読み込める)
   - 中身の形は本番と同じなので、本番のバックアップをテスト版に読み込んで試すことはできる(データは端末の中だけで動き、外には出ない)
   - フェーズ2以降のテスト版で書き出したファイルは、まだ本番で読めない形になります。マージ前の本番には読み込まないでください

## テスト版の反映のしかた

- `dev` のコードを `npm run build:test` でビルドし、できた中身(`dist`)だけを `hitotsuyane-test` リポジトリに送る
- `hitotsuyane-test` には、ビルドした中身だけを置く(ソースコードは置かない)
- この手順は、スクリプト(`scripts/deploy-test.mjs`)にまとめて、毎回同じように行えるようにする
- 反映したら、どの `dev` のコミットから作ったかを `hitotsuyane-test` のコミットの説明に書く

最初の反映は、フェーズ1の変更を入れる前の、今の `main` と同じ中身(テスト版の切り替えだけを足したもの)にします。

- 先にテスト版に本番のバックアップを読み込んでおくと、フェーズ2以降で「古い形のデータが、新しい版で正しく移行されるか」を、実際の更新と同じ流れで iPhone で確かめられるため

## GitHub での準備

GitHub CLI(`gh`)の準備ができたら、こちらで次を行います。

1. 公開リポジトリ `Creative-Hues/hitotsuyane-test` を作る
2. GitHub Pages を「`main` ブランチの一番上のフォルダから公開」に設定する
3. 最初の中身を送り、公開されたことを確かめる

`gh` を使わずに手で作る場合の手順:

1. GitHub の右上「+」→「New repository」
2. Owner を `Creative-Hues`、Repository name を `hitotsuyane-test` にし、「Public」を選ぶ。ほかは何も選ばずに「Create repository」
3. こちらで最初の中身を送ったあと、そのリポジトリの「Settings」→「Pages」を開く
4. 「Source」を「Deploy from a branch」、Branch を「main」「/ (root)」にして「Save」
5. 数分後に `https://creative-hues.github.io/hitotsuyane-test/` が開けば完了

## ブランチとマージの流れ

1. 準備とフェーズの作業は、すべて `dev` で行う
2. 各フェーズの段階ごとに `dev` にコミットし、push の前には止まって確認をもらう
3. フェーズが終わったら、テスト版に反映して iPhone で確認してもらう
4. OK が出たフェーズだけ、`dev` を `main` にマージする。マージは必ず確認をもらってから行う
5. フェーズ2以降(データの形が変わる)は、マージの前に必ず止まって声をかける。利用者にバックアップを取ってもらってからマージする
6. マージすると本番が更新され、利用者の画面に更新のお知らせの帯が出る(データの形が変わるときは強めのお知らせ)

あると安心な設定(任意):GitHub の「Settings」→「Branches」で `main` を保護し、直接 push できないようにする。必要なら手順をお伝えします。
